## Математика и данные

Сверены 50 исходных индикаторов, пять долей населения, десять весов, все 14 мер с ценами, лагами, областью действия и эффектами, три синергии и три конфликта.

```text
I'[d,k] = clip(I[d,k] + Σ(effect[m,k] × (8 − lag[m]) / 8) + synergies[d,k], 0, 100)
D[d]    = Σ(weight[k] × I'[d,k])
Score   = 0.7 × Σ(populationShare[d] × D[d]) + 0.3 × min(D[d]) − count(I'[d,k] < 40)
```

Синергии добавляются без повторного лага. Ограничение 0–100 выполняется после суммирования эффектов. Порог критичности строго ниже 40. Промежуточного округления и ограничения самого Score диапазоном 0–100 нет. Округление в интерфейсе не меняет арифметику.

Несовместимости: M1/M3 в любых районах; M4/M7 и M5/M13 только в одном районе. Городские меры оплачиваются один раз и действуют во всех пяти районах.

| Контроль | Бюджет | Итоговый Score | Критических индикаторов |
| --- | ---: | ---: | ---: |
| Исходное состояние | — | 52.55768 | 2 |
| M7 Нура, M8 Нура, M10 Нура, M12, M5 Сарыарка | 95 | 56.54307 | 0 |
| Замена M5 Сарыарка → M3 Нура | 100 | 57.20556 | 0 |
| M2, M3 Нура, M8 Нура, M9 Нура, M14 | 98 | 57.236735 | 0 |

У второго контрольного плана лучшая одиночная замена имеет Score 57.225545: прирост отрицательный, −0.01119. Это корректный результат поиска; его нельзя называть улучшением.

## Найденные и исправленные проблемы

1. UI показывал только первую ошибку плана. Теперь одновременно видны перерасход и все конфликты; в KK/EN ошибка отсутствующего района указывает ID меры.
2. Неверная дата из `localStorage` могла отображаться как `Invalid Date`. Она игнорируется, корректный план восстанавливается.
3. Локализованный анализ KK/EN не раскрывал отрицательные изменения индикаторов. Теперь явно показывает снижение, значения до/после и конкретные оставшиеся критические показатели.
4. При равенстве минимальных районных баллов карточки отмечали один район. Теперь отмечаются все слабейшие; ручной выбор района сохраняется.
5. Формулировка AI/fallback «остаётся слабейшим» была неверна при смене слабейшего района. Теперь описывается итоговое состояние, а при одинаковых минимумах/приростах перечисляются все районы.
6. Клиентский `fetch` не имел собственного срока ожидания. Добавлен тайм-аут 25 секунд и корректная отмена после чтения ответа; при сбое остаётся локальное объяснение. SDK ограничен 20 секундами, повторные обращения отключены.
7. API читал неограниченное тело JSON. Введён лимит 16 КиБ с учётом реально прочитанных байтов, даже при отсутствующем или ложном `Content-Length`.
8. Вход модели состоял преимущественно из текстовых карточек. Добавлены серверные расчёты стоимости, лагов, эффектов, дельт районов, синергий и кандидата на замену. Выход остаётся строго ограниченным идентификаторами проверенных фактов.
9. В документации движка оставалась заглушка автора; внутреннее задание участника могло быть принято за официальный источник. Автор указан по Git-истории, происхождение источников пояснено.

## Реальные проверки OpenAI

Выполнено ровно три запроса через официальный SDK и Responses API, модель `gpt-6-sol`. Во всех случаях получен `source: openai`; ключ использован только из существующего локального окружения, не копировался в репозиторий и не печатался.

| Сценарий | Проверенный результат | Время одного запроса |
| --- | --- | ---: |
| Официальный план и лучшая замена | 52.55768 → 56.54307; замена +0.66249 | 5 602 мс |
| План с отрицательным лучшим кандидатом | 57.236735; замена −0.01119 описана как снижение | 5 029 мс |
| Изменённые исходные данные районов | 48.91492 → 50.90031; критических 4 → 4 | 6 271 мс |

В третьей fixture изменены Нура S1=25/S2=20, Сарыарка E2=28, Есиль T1=35; production-каталог сохранён. Проверены JSON-схема, точное совпадение summary и сохранение всех фактов во всех четырёх разделах. Приоритизация может меняться, численные факты и их содержание — нет. Это три наблюдения, а не гарантия задержки или доступности провайдера.

Автоматические проверки дополнительно покрывают пустой/невалидный JSON модели, неизвестные/повторные ID, незавершённый ответ, ошибку провайдера, отказ сети, тайм-аут, отмену устаревшего ответа, подделку клиентского Score и неверные входные данные. Неверный план получает 400 до платного вызова; слишком большой запрос — 413. Эти ошибки не превращаются в фиктивный успешный расчёт.

## Чем решение отличается

Практическое отличие — проверяемое сравнение «текущий план → одна допустимая замена → районные последствия → применение». Оно позволяет показать на демо, откуда берётся рекомендация, кому она помогает и чем приходится пожертвовать. Советник работает и без сети.

AI получает рассчитанные сведения и выбирает приоритет фактов. Это ограниченная роль модели: формулировки и численные выводы формирует код. Называть такую систему свободно рассуждающим городским экспертом или утверждать, что у конкурентов нет похожего подхода, оснований нет.

## Границы проверки и продукта

- Синтетическая модель предназначена для учебного сравнения решений, а не прогноза реальной городской политики.
- Советник перебирает одну новую меру, отсутствующую в исходном наборе, и районы для неё. Перенос той же меры или глобальный перебор всех планов не выполняется.
- Изменённый датасет проверяется отдельной fixture на уровне расчёта и AI. Загрузки произвольного датасета в интерфейс/API нет; официальное задание требует общий исходный набор.
- OpenAI используется для русского анализа; казахский и английский анализ локальные.
- Публичный деплой не выполнялся. Локальная сборка и браузерные проверки не подтверждают доступность публичного сервиса.
- GitHub Actions на исходной main не запустился: аккаунт заблокирован из-за биллинга. Это инфраструктурный сбой до выполнения шагов, а не успешная проверка CI.
