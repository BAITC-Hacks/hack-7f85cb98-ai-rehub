# Часть 1. Расчётный движок

> Автор расчётного движка: Abdurrokhman Koblan ([@DoterDe](https://github.com/DoterDe)).
> Роль в команде: данные, формула, валидатор и тесты.

Команде передаётся TypeScript-модуль, который проверяет пять управленческих решений, рассчитывает Astana Quality of Life Score, показывает изменения по районам и подбирает варианты одной замены. Вместе с ним передаются единый каталог данных, типизированный API, тесты и команды воспроизводимой сборки. Это точка входа в документацию моего вклада в проект «Аким на 5 часов».

## Назначение и ответственность

Движок позволяет сравнивать распределение ограниченного бюджета по пяти направлениям: транспорт, озеленение и экология, социальная инфраструктура, безопасность, городские сервисы. Все пользователи начинают с одинаковых данных и бюджета **100 условных единиц**.

Моя зона ответственности — данные и правила модели, расчёт показателей, проверка решений, сравнение районов, советник и проверка корректности расчётов. Frontend, AI API, общий интерфейс и интеграция приложения относятся к работе других участников. Этот документ описывает готовность расчётной части.

## Что реализовано

- **Данные:** 5 условных районов, по 10 индикаторов в каждом, доли населения и 14 мероприятий с ценами, эффектами, областью действия и лагами. Каталоги защищены от изменения; шкала индикаторов — 0–100, больше означает лучше.
- **Ограничения:** ровно 5 разных `measureId`, стоимость не выше 100, максимум 2 мероприятия одного направления. Все пять направлений доступны, но охватывать каждое в одном плане не требуется.
- **Область действия:** районная мера требует `districtId`; у городских M2, M6, M12 и M14 это поле полностью отсутствует. Городская мера оплачивается один раз, её эффект применяется к каждому району.
- **Несовместимости:** M1 и M3 нельзя сочетать вообще; M4 и M7, а также M5 и M13 нельзя сочетать в одном районе.
- **Лаги и синергии:** эффект зависит от задержки реализации; три сочетания мер дают дополнительные фиксированные эффекты.
- **Результат:** Score, бюджет, критические индикаторы, значения до/после и изменения каждого района, реализованные эффекты и сработавшие синергии.
- **Советник:** полный перебор допустимых вариантов одной замены, до трёх альтернатив по Score и отдельные стратегии по минимальному районному баллу и лагу новой меры.

## Формула и порядок расчёта

Горизонт модели — **8 кварталов**. Для мероприятия с лагом `L` реализуется доля `(8 − L) / 8` каждого эффекта, включая отрицательные эффекты.

Расчёт выполняется в следующем порядке:

1. Проверить весь план; при ошибках вернуть невалидный результат без итогового Score.
2. Умножить эффекты выбранных мер на долю реализации и распределить их по соответствующим районам.
3. Добавить фиксированные синергии без повторного применения лага: M1+M2 → T1+2 в районе M1; M10+M12 → B1+2 в районе M10; M5+M6 → E2+2 в районе M5.
4. Сложить все эффекты с исходными значениями и только затем один раз ограничить каждый индикатор диапазоном 0–100.
5. Рассчитать районные баллы, среднее с учётом населения, минимальный районный балл и число критических индикаторов.

Для района `d` и его итоговых индикаторов `I[d,i]`:

```text
D[d] = Σ вес[i] × I[d,i]
CityAverage = Σ доля_населения[d] × D[d]
Weakest = min D[d]
Ncrit = число пар «район, индикатор», в которых I[d,i] < 40

Astana Quality of Life Score = 0.7 × CityAverage + 0.3 × Weakest − Ncrit
```

Веса T1/T2 — 0.10/0.10; E1/E2 — 0.09/0.11; S1/S2 — 0.11/0.11; B1/B2 — 0.09/0.09; C1/C2 — 0.10/0.10. Названия индикаторов и значения долей населения находятся в каталогах выше.

Порог критичности строгий: значение **40 уже не критическое**. Итоговый Score не ограничивается диапазоном 0–100. Входы и промежуточные результаты не округляются; форматирование выполняется только при показе пользователю. Проверки десятичных контрольных значений используют допуск `1e-8`.

## Публичный API и рабочий пример

`getBaseline()` возвращает отдельное исходное состояние. `validateScenario(input)` проверяет план. `evaluateScenario(input)` повторно проверяет его и рассчитывает результат. `findBestReplacement(input)` принимает массив решений и возвращает исходный результат, альтернативы и необязательных победителей стратегий. Три функции с входом принимают `unknown`, поэтому проверка действует и для данных, полученных из JSON.

Следующий пример выполняется из корня репозитория на Node.js ≥22.18:

```sh
node --input-type=module <<'JS'
import {
  getBaseline, validateScenario, evaluateScenario, findBestReplacement,
  EXAMPLE_DECISIONS,
} from './src/domain/index.ts';

const baseline = getBaseline();
console.log('База:', baseline.score.toFixed(5)); // 52.55768

const validation = validateScenario(EXAMPLE_DECISIONS);
if (!validation.valid) throw new Error(validation.errors.join('; '));

const result = evaluateScenario(validation.decisions);
if (!result.valid) throw new Error(result.errors.join('; '));
console.log('Цена / остаток:', result.totalCost, result.remainingBudget); // 95 / 5
console.log('Score:', result.finalScore.toFixed(5)); // 56.54307
console.table(result.districts.map(d => ({
  район: d.name, до: d.scoreBefore, после: d.scoreAfter, изменение: d.scoreDelta,
})));

const advisor = findBestReplacement(validation.decisions);
const best = advisor.bestByScore;
if (best) {
  console.log('Замена:', best.removed.decision, '→', best.added.decision);
  console.log('Score / прирост:', best.result.finalScore.toFixed(5),
    best.scoreGain.toFixed(5)); // 57.20556 / 0.66249
}

const invalid = evaluateScenario([]);
console.log(invalid.valid, invalid.finalScore); // false null
JS
```

Формат одного решения: `{ measureId: 'M7', districtId: 'nura' }` для районной меры и `{ measureId: 'M12' }` для городской. Типы результатов экспортируются из той же точки входа.

## Неправильный ввод

Проверяются структура массива и объектов, известные ID, обязательность района, количество решений, повторы, направления, бюджет и несовместимости. Дополнительные поля вроде `cost` и `finalScore` запрещены: цену и эффекты движок берёт из каталога. У городской меры недопустимо даже `districtId: undefined` или `districtId: null`.

При ошибке `evaluateScenario` возвращает `valid: false`, `errors: string[]`, структурированные `errorDetails`, **`finalScore: null` и `scoreDelta: null`**. Результаты районов и эффектов остаются пустыми. Базовые показатели доступны, но не выдаются за результат принятого плана. Если стоимость нельзя вычислить, `totalCost` и `remainingBudget` тоже равны `null`; при известных ценах сохраняются вычисленные суммы.

Перед обращением к численным результатам потребитель обязан проверить `result.valid`. Для невалидного ввода советник возвращает пустые альтернативы, нулевые счётчики и не возвращает победителей. Пустой массив не заменяет `getBaseline()`.

## Установка, тестирование и сборка

Требуются Node.js ≥22.18, npm и доступ к репозиторию. Из корня checkout проекта:

```sh
npm ci --ignore-scripts
npm run typecheck:engine
npm run test:engine
npm run test:legacy
npm run build:engine
npm run smoke:engine
```

Зависимости закреплены в [package-lock.json](../../package-lock.json). Сборка создаёт ESM JavaScript, декларации типов и sourcemaps в `dist/engine`; готовый импорт — `dist/engine/domain/index.js`. Для расчётов не нужны AI-ключи или сетевые запросы. Дополнительные команды `npm run benchmark:engine` и `npm run smoke:browser:prepare` описаны в [handoff](handoff.md).

## Подключение frontend и AI

**Frontend-разработчику:** импортировать функции и каталоги из `src/domain/index.ts`, хранить массив решений в указанном формате, показывать ошибки валидации и остаток бюджета. Для сравнения использовать `result.districts`, для рекомендаций — `findBestReplacement`. Проверять `valid` и наличие необязательного победителя перед отображением чисел. В Next.js использовать сборщик и alias приложения. При объединении веток сохранить зависимости и scripts приложения, добавив команды движка.

**AI-разработчику:** на сервере заново вычислять результат по присланным решениям. Передавать AI успешный `ScenarioResult` и при необходимости `AdvisorResult`; модель объясняет уже рассчитанные факты. Предложенные AI решения сначала валидируются и рассчитываются кодом. `contributions` описывает эффекты, но его `observedDistrictDeltas` содержит суммарные изменения соответствующих индикаторов во всём плане, а не независимый вклад меры в Score.

Старые `simulateScenario` и `validateDecisions` заменены новым контрактом; [карта миграции](handoff.md#миграция-старого-контракта) поясняет соответствие полей. Старый каталог `tests/reference/engine` предназначен для регрессий и не подключается в приложение.

## Ограничения модели

- Данные, стоимость и эффекты синтетические. Они служат для учебного сравнения сценариев; подтверждённых прогнозов реальных городских последствий модель не даёт.
- Советник меняет ровно одну меру на отсутствующую во всём исходном наборе и перебирает районы новой меры. Перенос той же меры в другой район, несколько замен одновременно и глобальный поиск всех планов не выполняются.
- Лучшая допустимая замена может иметь отрицательный прирост. Например, для плана за 98 единиц лучший сосед даёт Score **57.225545**, то есть **−0.01119** относительно исходного. Такой вариант нельзя называть улучшением.
- Стратегия `bestFastImpact` предпочитает меньший лаг новой меры по каталогу. Это правило ранжирования, а не обещание сроков или эффекта в реальном городе.
